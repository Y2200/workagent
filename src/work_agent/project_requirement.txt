一.甲方要求
1.把模型(豆包)嵌入工作群(微信或企业微信)。
2.机器人监督每天的工作进度。

二.初步目标
企业工作督导Agent完整落地实现步骤
整体技术栈：Python+FastAPI + LangChain‑LangGraph + Redis(队列+缓存) + 向量数据库(FAISS) + 企业微信API + 火山豆包API
整体流程：企微推送消息 → 接入服务校验预处理 → 消息队列异步分发 → Agent业务编排 → RAG知识库比对 → 结果推送企微，附带定时任务、安全校验。
阶段1：前期准备工作（1‑2天）
账号与资源申请
1. 注册企业微信管理后台，创建自建应用，获取企业ID、AgentId、Secret，配置消息推送回调地址；
2. 注册火山引擎，开通豆包API，获取API‑Key，签订商用协议，开启调用日志不落地；
3. 租用1台云服务器（4核8G，CentOS/Ubuntu），开放80、443端口，安装Docker、Redis、Python3.10；
4. 本地搭建开发环境：安装fastapi、langchain、langgraph、redis、faiss‑cpu、pypdf、celery。

阶段2：开发接入层（接口+消息预处理，第2‑3天）
步骤1：开发FastAPI接口，接收企业微信推送
1. 编写接口，接收企微POST推送的群聊消息；完成签名校验，防止恶意请求；
2. 统一数据预处理（ data_filter.py ）
正则脱敏：手机号、报价、客户全称、内部编号替换为掩码；
过滤无效消息：表情包、图片、闲聊无关语句；
格式化数据：封装消息发送人、发送时间、文本内容、群ID；
3. 判定流量类型
实时消息：推入Redis‑Celery异步队列，立刻给企微返回200，避免企微重复推送；
定时任务（每日18:00汇总日报）：由定时脚本生成任务，丢入队列。
核心作用：接入层只做校验与分发，不调用大模型，防止高并发压垮服务。
阶段3：搭建异步任务系统（解决高并发，第3‑4天）
1. 部署Redis，作为消息队列与缓存中间件；
2. 配置Celery，创建消费者Worker；可以启动多个Worker实例实现分布式扩容；
3. 任务分级：
普通任务：聊天实时分析；
重型任务：周报生成、批量历史数据统计，单独分配Worker；
4. 配置限流与重试：
令牌桶算法限制单群每分钟最大请求数；
调用LLM出现429限流时，采用带随机抖动的指数退避重试，最多重试3次；
错误率超过阈值自动熔断，降级为固定模板输出。
阶段4：搭建RAG知识库模块（第4‑5天）
1. 文档加载：读取static/knowledge下的部门规章、项目计划文件；
2. 文本处理：LangChain文本分块，去除冗余内容，生成向量；
3. 向量库：使用FAISS本地向量库（私有化交付首选）；线上生产可替换为Milvus；
4. 封装检索函数：Agent需要校验任务时，自动检索对应项目要求；
5. 权限控制：不同团队只能检索自身对应的知识库文件。
阶段5：基于LangGraph开发核心Agent工作流（核心部分，5‑7天）
定义全局状态State
存储全局共享数据：当日人员任务列表、未完成清单、知识库检索结果、告警标记、执行日志。
划分5个执行节点（Node）
1. node_parse_msg：解析群消息，提取每个人今日完成的工作；
2. node_rag_check：调用RAG，对比项目要求，判断任务是否达标；
3. node_judge_task（判断边，代码逻辑）
存在逾期未完成任务 → 进入提醒节点；
任务全部完成 → 跳转生成日报节点；
4. node_send_warn：生成提醒消息，推送至企微；设置标记，间隔2小时二次提醒，多次未完成则上报负责人；
5. node_generate_report：汇总全天数据，生成标准化日报，发送工作群。
开启Checkpoint快照
每执行完一个节点自动保存状态，服务器重启后可以继续执行当天任务，不用重新处理全部聊天记录。
系统提示词约束
固定规则：禁止导出原始完整聊天记录，不泄露内部资料，输出格式固定。
阶段6：安全体系开发（7‑8天）
1. 密钥管理：豆包API‑Key、企微密钥全部配置在服务器环境变量，代码内不明文存储；定期轮换密钥；
2. 数据库安全：聊天记录加密存入数据库，数据库禁止公网访问，仅本机程序可调用；
3. 全链路日志：记录每条请求的操作人员、原始内容、传给大模型的报文、返回结果；
4. 输出校验：拦截模型输出中包含的涉密信息，防止AI误泄露资料；
5. 私有化适配方案：提供两套模式，公有API模式 / 本地私有化大模型部署模式。
阶段7：定时任务与推送模块（第8‑9天）
1. 采用APScheduler配置定时任务：
每日18:00触发自动汇总日报；
21:00复盘未完成任务，统一上报领导；
2. 封装企微消息发送函数，支持文本、表格格式消息推送；
3. 异常兜底：任务执行失败，自动给管理员发送告警消息。
阶段8：整体联调、压力测试、优化（9‑11天）
1. 模拟大量消息并发涌入，测试队列堆积、多Worker扩容效果；
2. 优化缓存：对重复问题、固定Prompt前缀开启KV缓存，减少token消耗；
3. 上下文优化：只保留7天内上下文，久远数据仅存数据库，不传入大模型；
4. 异常测试：模拟LLM接口宕机、服务器重启，验证熔断机制、断点续跑功能。
阶段9：部署交付（第12天）
1. 使用Nginx做反向代理，配置HTTPS域名；
2. 编写部署文档、用户使用手册；
3. 交付材料：源码、部署步骤、环境配置文档、运维手册；
4. 交付规范：客户自行提供大模型API‑Key，我方不持有密钥；讲解数据隐私方案。
